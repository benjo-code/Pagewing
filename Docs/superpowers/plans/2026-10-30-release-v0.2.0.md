# Release v0.2.0 – Implementierungsplan

> **Für agentische Ausführung:** Erforderlicher Unter-Skill: `superpowers:subagent-driven-development` (empfohlen) oder `superpowers:executing-plans`. Die Schritte nutzen Checkbox-Syntax (`- [ ]`).

**Ziel:** Das Release `v0.2.0` (Milestones 8.1 bis 12.1: Updater, Speichern, Annotieren, Zeichnen, Formulare, sichtbare Unterschrift, öffentliches Repo) ist vorbereitet. Die Abnahme besteht **nur aus automatisierten Prüfungen**; alle Handprüfungen des Projektinhabers sind in die Abnahme von `v1.0.0` verschoben. Veröffentlicht wird nur auf ausdrückliche Anweisung.

**Architektur:** Drei Phasen. Phase 1 ist Roadmap- und Workflow-Pflege auf `feature/release-v0-2-0` (PR nach `dev`). Phase 2 sind Nachweisläufe (CI auf `dev`, Linux-Tests im Container, Trockenlauf, Hardware-Messung) ohne Codeänderung. Phase 3 ist das Veröffentlichen nach `CLAUDE.md`, Abschnitt „Releases“. Neue Funktionen kommen nicht dazu.

**Tech Stack:** `Docs/roadmap.json` und `tools/roadmap.cs`, `.github/workflows/{ci,release,hardware-measure}.yml`, `tools/package.cs`, Docker (Linux-Tests), `gh`.

**Spec:** [Gesamt-Spec](../specs/2026-10-16-pagewing-design.md); Roadmap-Eintrag „Release `v0.2.0` – Abnahme“ in `Docs/roadmap.json`; [packaging/README.md](../../../packaging/README.md), Abschnitte „Release bauen“ und „Update prüfen“; Plan des Vorgängers [2026-10-23-release-v0.1.0.md](2026-10-23-release-v0.1.0.md). Anweisung des Projektinhabers (2026-10-30): „Nur automatisierte Tests, manuelle Abnahmen aufschieben auf v1.0.0“, Messung auf dem Haupt-PC (`hardware-measure.yml`) darf dabei sein.

## Entscheidungen

Vom Projektinhaber: (1) Abnahme nur automatisiert, Handprüfungen nach `v1.0.0`; (2) `hardware-measure.yml` gehört zur Abnahme. **Meine Entscheidungen (vom Projektinhaber zu prüfen):**

- **Gemischte Kriterien werden geteilt:** Was ein Test belegt, wird Kriterium von `v0.2.0`, der Handprüf-Rest geht wörtlich nach `v1.0.0`. Nichts wird gestrichen.
- **Linux-only-Tests laufen im Container** (`ubuntu:24.04` per Docker Desktop auf dem Entwicklungsrechner, Quelle über `git archive`), weil die CI sie zwar mitlaufen lässt, aber pro Klasse nichts belegt. Dazu zählt der CUPS-PDF-Test (automatisiert, Einrichtung wie in `CLAUDE.md`, „Drucken“).
- **Nicht dabei, nach `v1.0.0`:** der Beweis, dass `PauseCallbackStressTests` mit dem *alten* Pause-Rückruf abstürzt (verlangt einen absichtlich kaputten Stand), die Fork-PR-Probe (zweites GitHub-Konto), `--measure-scroll` mit `scroll-text-dense-10-signatures.pdf` (die Datei entsteht erst durch einen Test mit `PAGEWING_MEASURE_OUT`, nicht im Workflow).
- **`forms-basic.pdf` kommt in die Scroll-Schritte von `hardware-measure.yml`** (M11 verlangt es; ein Einzeiler je Schritt), damit die Messung ohne Handarbeit läuft.
- **Der Trockenlauf baut `dev`** (`-f ref=dev`), nicht einen eigenen Release-Branch; der Lauf mit Vorabversion `v0.1.1` (Lauf 41082877095, einschließlich `manifest`) hat den Upload- und Signaturweg schon bewiesen.
- **Risiko, im Changelog offen genannt:** Der Updater ist nie gegen ein echtes Release gelaufen. `v0.2.0` auf `v0.3.0` ist zugleich der erste Ende-zu-Ende-Test.

## Globale Randbedingungen

- Budgets und Startzeit-Check werden nicht gelockert, keine Tests übersprungen oder abgeschwächt (`CLAUDE.md`, „Qualität & Nachweis“).
- Veröffentlichen, Tags, Releases, Merges nach `main` und Workflow-Läufe mit `upload=true` nur auf ausdrückliche Anweisung; der Job `manifest` wartet auf die Freigabe des Projektinhabers im Environment `release-signing`.
- Der private Signaturschlüssel erscheint nie in Dateien, Logs oder Chat; kein Agent liest ihn.
- Kein Text nennt etwas „rechtsgültig“ oder eine Signatur „gültig“; der Changelog behauptet keine Handprüfung, die nicht stattfand.
- Tests schreiben nie in die echte Registry oder den echten Benutzerordner. Testnamen ohne Unterstriche.
- Tag-Form: `v0.2.0` (SemVer-Regex aus `release.yml`, geprüft von `package.cs selftest`, `TagRuleParts`). `Directory.Build.props` bleibt bei `0.0.0`; die Version kommt aus dem Tag (`-p:Version`).
- „Fertig“ heißt: `dotnet build Pagewing.slnx`, `dotnet test Pagewing.slnx`, `dotnet format Pagewing.slnx --verify-no-changes`, `dotnet run tools/roadmap.cs -- check`, `dotnet run tools/package.cs -- selftest`, `dotnet run tools/licenses.cs -- check` grün, Befehl und Ergebnis genannt.

## Review-Schwerpunkte

1. **Kriterium geht beim Verschieben verloren:** 13 alte Kriterien, nach der Teilung 7 neue in `v0.2.0` und 12 in `v1.0.0` (8 ganz, 3 Reste, 1 neu) → Task 1, Zählprüfung.
2. **Release mit Platzhalterschlüssel:** `preflight` verweigert den Upload; zusätzlich der Test mit `PAGEWING_REQUIRE_RELEASE_KEY=1` vor dem Tag → Phase 3, Schritt 1.
3. **Tag existiert schon oder liegt nicht auf `main`/`dev`:** `preflight` bricht ab; vorher `git ls-remote --tags origin v0.2.0` leer → Phase 3, Schritt 1.
4. **Teilweise hochgeladenes Release** (ein Bau-Job scheitert, der andere hat hochgeladen) → Phase 3, „Nacharbeit“; kein Löschen ohne Anweisung.
5. **Hardware-Messung ungültig** (Runner offline, Warnung zum Frame-Takt, Bildschirm gesperrt): offline bleibt der Job in der Warteschlange, eine `Warnung:`-Zeile macht die Zahlen ungültig → Phase 2, Schritt 4; nie Budgets anpassen, um grün zu werden.
6. **Changelog behauptet zu viel:** Der Abschnitt `[0.2.0]` nennt die nicht von Hand geprüften Punkte → Task 3, Schritt 3, mit `grep`-Prüfung.
7. **Linux-Lauf im Container prüft etwas anderes als die CI:** Quelle per `git archive` des Commits (keine Windows-`obj`-Ordner), Ergebnis „bestanden“ und „übersprungen“ je Klasse getrennt gelesen → Phase 2, Schritt 2.

## Selbstprüfung

- **Abdeckung:** Jedes der 13 bisherigen Kriterien hat in der Zuordnungstabelle von Task 1 ein Ziel (`v1.0.0`, K3, K4, K5 oder geteilt). Die Anweisung „nur automatisiert, Hardware-Messung dabei“ steckt in K1 bis K7, Task 2 und Phase 2.
- **Typkonsistenz:** K1 bis K7 heißen in Task 1, Phase 2 und Phase 3 gleich; die Zahlen 7 und 12 stimmen mit der Tabelle (8 ganz + 3 Reste + 1 Fork-Probe).
- **Grenzen:** Ohne den Projektinhaber geht nicht: Runner des Haupt-PCs starten, Docker Desktop starten falls aus, Freigabe von `manifest`, jede Veröffentlichung. Nicht geprüft bleiben bis `v1.0.0` alle Handprüfungen aus der Tabelle; der Changelog sagt das.
