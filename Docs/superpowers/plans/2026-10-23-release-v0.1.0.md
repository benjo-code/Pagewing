# Release v0.1.0 – Implementierungsplan

> **Für agentische Ausführung:** Erforderlicher Unter-Skill: `superpowers:subagent-driven-development` (empfohlen) oder `superpowers:executing-plans`. Die Schritte nutzen Checkbox-Syntax (`- [ ]`).

**Ziel:** Das erste Release `v0.1.0` („schneller Viewer“, Milestones 0 bis 8) ist vorbereitet: Alle Punkte „Vor dem ersten Release“ sind erledigt, der Trockenlauf des Release-Workflows ist auf beiden Runnern grün, und der Projektinhaber kann die Abnahme durchführen und das Release auf Anweisung veröffentlichen.

**Architektur:** Drei Phasen. Phase 1 sind Code- und Workflow-Änderungen auf dem Branch `feature/release-v0-1-0` (PR nach `dev`, von Claude umsetzbar). Phase 2 sind Läufe auf den Runnern und die manuelle Abnahme (Projektinhaber, Claude begleitet). Phase 3 ist das Veröffentlichen (`release/v0.1.0` → `main`, `gh release create`), **nur auf ausdrückliche Anweisung**. Neue Funktionen kommen nicht dazu.

**Tech Stack:** `tools/package.cs` (Einzeldatei-Werkzeug mit `selftest`), `.github/workflows/release.yml`, xUnit (`tests/Pagewing.App.Tests`), `gh`.

**Spec:** [Gesamt-Spec](../specs/2026-10-16-pagewing-design.md), Roadmap-Eintrag „Release v0.1.0“ in `Docs/roadmap.json` (Abnahmekriterien), [packaging/README.md](../../../packaging/README.md), `Docs/DECISIONS.md` (Einträge „Mindest-glibc 2.35 (vorläufig) …“, „Offen: Quellangebot für libfuse und type2-runtime (M8)“, „Verteilung: Nicht-Ziele und offene Fragen …“).

## Befund beim Planen (2026-10-23)

- **Der blockierende glibc-Schritt von `release.yml` scheitert heute.** CI-Lauf 39858081105 (`build-linux`): Runner ist Ubuntu 26.04 mit glibc 2.43, Docker 29.1.3 ist vorhanden. `check-binary --max-glibc 2.35` meldet `out/app/Pagewing: verlangt GLIBC_2.38`; `libpdfium.so`, `libSkiaSharp.so`, `libHarfBuzzSharp.so` und die CLI bestehen. Ein Release-Lauf bräche also vor dem Paketieren ab.
- **Der Trockenlauf geht so nicht.** `release.yml` checkt `ref: inputs.tag` aus; vor `gh release create` gibt es den Tag `v0.1.0` nicht. Der Trockenlauf braucht einen eigenen Eingabewert `ref`.
- **Symbolgrößen:** `Docs/design/icons/linux/hicolor` hat zehn Größen (inklusive 22 und 96) und `.deb` und AppImage liefern alle aus; `LinuxDefaultAppService.IconSizes` kopiert beim AppImage-Standardprogramm nur acht (ohne 22 und 96).

Jede hat eine Voreinstellung (fett); ohne Antwort gilt sie.

4. **Avalonia-Telemetrie beim Bauen.** **`AVALONIA_TELEMETRY_OPTOUT=1` in allen Workflows setzen** oder bewusst zulassen (betrifft nur Build-Rechner, nicht die App).

## Globale Randbedingungen

- Keine neuen Funktionen, Pakete oder Architekturentscheidungen (Milestone-Disziplin); Auto-Update gehört zu Milestone 8.1, nicht hierher.
- Budgets und Startzeit-Check werden nicht gelockert. Native AOT, Warnungen sind Fehler.
- Release-Dateinamen und Tag-Regex bleiben stabil (`Pagewing-<Version>-win-x64-setup.exe`, `…-portable.zip`, `pagewing_<Version>_amd64.deb`, `Pagewing-<Version>-x86_64.AppImage`, `SHA256SUMS-windows.txt`, `SHA256SUMS-linux.txt`); `AppId` des Installers ändert sich nie.
- Tests schreiben nie in die echte Registry oder den echten Benutzerordner. Testnamen ohne Unterstriche. Änderungen an `tools/package.cs` beginnen und enden mit `dotnet run tools/package.cs -- selftest`.
- Veröffentlichen, Tags, Releases und Merges nach `main` nur auf ausdrückliche Anweisung (CLAUDE.md, „Zusammenarbeit“). Das Repo ist privat; das Release ist daher nur für Berechtigte abrufbar.
- „Fertig“ heißt: `dotnet build Pagewing.slnx`, `dotnet test Pagewing.slnx`, `dotnet format Pagewing.slnx --verify-no-changes`, `dotnet run tools/roadmap.cs -- check` grün, Befehl und Ergebnis genannt.

## Review-Schwerpunkte

Eingaben und Bedingungen, die das Release treffen können und von der Spec nicht abgedeckt sind; jede hat einen Test oder einen festen Prüfschritt:

1. **Tag-Form:** `v0.1.0-rc.1` muss bauen (`.deb`-Version `0.1.0~rc.1`), `V0.1.0`, `v0.1`, `v0.1.0.` und `0.1.0` müssen abgelehnt werden → Task 2.
2. **Beide Regeln gleich:** Die Tag-Regex steht zweimal in `release.yml` (PowerShell und bash); driften sie, baut ein Betriebssystem, das andere nicht → Task 2.
3. **Binary verlangt neuere C++-Laufzeit als das Ziel** (`GLIBCXX_3.4.xx`), obwohl glibc passt → Task 3.
4. **AppImage als Standardprogramm ohne Symbole 22/96;** `xdg-mime default` meldet Erfolg, obwohl nirgends ein `pagewing.desktop` liegt → Tasks 4 und 5.
5. **Teilweise hochgeladenes Release** (ein Job scheitert, der andere hat schon hochgeladen) → Phase 3, Schritt „Nacharbeit“; kein Löschen ohne Anweisung.
6. Version in der App: `AppInfo.Version` muss `0.1.0` zeigen, nicht `0.0.0` (`Directory.Build.props` setzt `0.0.0`, der Workflow übergibt `-p:Version`) → Phase 2, Schritt 6.

## Selbstprüfung

- **Abdeckung:** Jeder offene Punkt der Release-Abnahme in `Docs/roadmap.json` hat einen Ort: Mindest-glibc (Task 1), GLIBCXX (3), Tag-Regex (2), Symbolgrößen (4), `xdg-mime` (5), Quellangebot (6), Trockenlauf (Phase 2.2), Startzeit-Budgets (2.3), Windows/Linux-Handprüfungen (2.4 bis 2.5), Drucken und Screenreader (2.7), eine Woche Alltagsnutzung (2.8), Verschieben der portablen ZIP (2.4). Die Telemetrie-Entscheidung (Task 7) ist aus M8 übernommen, kein Pflichtpunkt der Abnahme.
- **Typkonsistenz:** `DefaultMaxGlibc` (Task 1) und `DefaultMaxGlibcxx` (Task 3) hängen an derselben Entscheidung 1; `IconSizes` (Task 4) und `LinuxDefaultAppService.MakeDefaultAsync` (Tasks 4 und 5) sind dieselbe Datei, Task 5 baut auf Task 4 auf.
- **Grenzen:** Nicht geprüft werden kann ohne Projektinhaber: echte Drucker, frische Systeme, Screenreader, die eine Woche Nutzung und der Haupt-PC-Runner. Das steht oben in Phase 2 mit den Befehlen.
